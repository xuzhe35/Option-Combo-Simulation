## 2. 结论

隔离边界、未知值诚实性、父子去重和证据保留的方向符合设计，可以保留：

- 页面不加载交易壳，不用 WebSocket / localStorage / IndexedDB；服务只认 loopback，检查 Host 防 DNS 重绑定，
  拒绝 `Origin: null`；不写日志、不持久化图片。
- generation 计数与 `sourceHash`、尺寸绑定，迟到或错图的识别回复被丢弃。
- 空白保持 null、不补零；组合父行与分组不进入 `positions`；JSON 校验父子循环、伪造腿列表和未映射源行。
- 代码中没有 ticker 字典或 NO→NQ 类替换；首轮值、重读值及坐标随 JSON 保留。
- 本轮新增仓库文件中未扫到真实账号（排除合成的 `U1234567` / `U0000000`）。

主要问题是**列归属**：列边界由固定比例推算，表头只检查是否存在、不检查位置。
列宽或列顺序不同时，数值会落到相邻列而不报错；计划 §6.4 将列归属错误定为阻断项。

## 3. 逐项意见、证据与验收要求

### A1 — 列边界不按表头定位，列错位不报错（高）

**位置：** `js/portfolio_snapshot_ocr.js:8`（`EDGES`）、`:156–164`；对照 `scripts/portfolio_snapshot_vision.swift:142–151`。

**原因：** 表头识别只要求同一行出现 INSTRUMENT、MARK、POS（`/POS\b/` 甚至可匹配 POSITION）。
随后仅用 FIN（或 INSTRUMENT）与 MARK 两点求 `scale` / `shift`，把一套为当前布局标定的固定比例推到全部 12 列。
其余列名（COST BASIS、MKT VALUE、DELTA DLLRS 等）在不在预期列内，没有任何核对。
这与计划 §6.3「先根据表头建立列索引」不符。Swift 端的数量重读已检查 POS 是否落在数量列，前端没有同样检查。

**合成复现：** 表头为 FIN / INSTRUMENT / MARK / `MKT VALUE`（位于原 POS 位置）/ POS（右移到 .60）。
一行 `ABC 12.34 14,808 -3` 的结果为：`quantity = "14808"`，`deltaDollars = "-3"`，`marketValue = null`，`issues = []`。

**真实数据复现：** 对两张私有原图的首轮识别结果，把左边界大于 0.40 的词整体右移，模拟用户拉宽 COST BASIS 列。
仅统计「新值非空、解析无问题、与原结果不同」的字段，即静默错值：

| 右移 | 新图（18 条） | 旧图（15 条） |
| --- | --- | --- |
| 1.5% 宽度 | UNRLZD P&L 4 | 0 |
| 2.5% 宽度 | AVG PRICE 9、UNRLZD P&L 13、MKT VALUE 2、DELTA DLLRS 2 | AVG PRICE 3、UNRLZD P&L 7 |
| 4% 宽度 | MKT VALUE 15、AVG PRICE 18、UNRLZD P&L 17、DELTA DLLRS 18、THETA 11、LAST 8、IV 2 | MKT VALUE 11、AVG PRICE 15、UNRLZD P&L 15、DELTA DLLRS 14 等 |

右移时数量多变为 null 并被提示；但金额列整体串位且不报错。换列（而非拉宽）时，数量本身也会被静默读错（见合成复现）。

**修复要求：**

1. 每一列的边界由该列表头标签的实际坐标推出；任何预期标签缺失、顺序不符或落在错误区间，拒绝识别并给出中文原因。
2. 把列标定从 JS 与 Swift 两份常数收敛为一个来源，或由前端把列区间传给辅助程序（见 A12）。
3. 实现计划 §6.3 已写但未做的金额核对：STK 行 `q × MARK` 与 `MKT VALUE` 在显示舍入内比较，不符只生成疑点，不自动修改。

**验收：** 新增测试覆盖换列、拉宽单列、删除一列、表头带排序箭头；对两张私有原图的拉宽模拟，结果必须是「拒绝」或「全部列正确」，不得出现静默错值。

### A2 — 重读改写的关键字段在批量确认后没有任何提示（中）

**位置：** `js/portfolio_snapshot_ocr.js:63–103`（短代码重读）、`:114–141`、`:234–252`（数量重读）；`js/portfolio_snapshot_core.js:8–22`、`:59–67`。

**原因：** 两次放大重读一致时，描述列里的标的、CALL/PUT、交易类别会被改写，空数量会被补出。
这些改动只记录在 `fieldEvidence.corrections` 和界面徽标中，不进入 `issues`；「批量确认全部」之后不再有任何提示。

两次重读来自同一引擎、同一片像素，不是独立证据。最敏感的是补出的数量：首轮完全没读到的「-1」，如果 3× 与 4× 都漏掉负号，会以「1」被采纳。计划 §3.2 第 5 条与 §6.4 把错号定为阻断项。

**修复要求：**

- 被机器改写或补出的关键字段（quantity、symbol、right、tradingClass）带持久标记，不随批量确认消失。
- 批量确认时列出这些字段（行、字段、首轮值 → 采用值），用户确认后再记为已核对。
- 尊重用户已确认的批量确认流程：提示，而不是强制逐行点击。

### A3 — 弹窗/工具栏无 `decoration` 归类，结构疑点无处理入口（中）

**位置：** `js/portfolio_snapshot_ocr.js:181`、`:204`、`:221`；`js/portfolio_snapshot_core.js:44–50`；`js/portfolio_snapshot_schema.js:78`。

**原因：**

- 计划 §3.1 定义了 `decoration` 行，但实现与 schema 都没有这个类型。
- 表头下方以字母开头的任意一行都会进入候选。单个大写词（如 `OK`、`NOTE`）被 `atomicLike` 当作股票代码，
  合成复现得到 `["OK","STK",null]` 一条持仓。
- 普通句子成为 `unclassified` 并写入 `structureIssues`。`reviewStatus` 要求结构疑点为空，界面又没有删除行、
  改行类型或确认疑点的入口；因此只要有一行弹窗文字，快照就永远到不了 `reviewed`。
  P4 的存档门槛（§5.3「已逐项确认未解决问题」）会被这道门挡住。
- 现有排除规则 `/^(Order|Complete|U\d{3,})\b/i` 实际上是按样例图写的词表，与「不按样例写分支」的原则不一致。

**修复要求：** 增加 `decoration` 行类型或「排除此行」操作（保留原文和原因）；为结构疑点提供逐项「已核对、接受不完整」的记录；
去掉样例词表，改为依据位置（例如表格区域外、与列结构不对齐）判断。这部分可与 P3「父子处理」一起交付，但应在 P4 之前完成。

### A4 — 导出 JSON 含原始识别全文，且体积会超过导入上限（中）

**位置：** `js/portfolio_snapshot_ocr.js:278–285`（`originalWords` / `originalLines` / `originalRereads` / `unmatchedRows`）；
`js/portfolio_snapshot.js:424–433`（格式化导出）、`:442`（导入 1 MiB 限制）。

**账号问题：** 旧图的私有浏览器导出中，`originalLines` 与 `unmatchedRows` 各有 1 处弹窗通知里的账号（仅计数，未读取或记录具体值）。
计划 §3.2 第 1 条要求忽略通知中的账号候选；该 JSON 一旦外传或在 P4 入库，就带出了未经用户填写的账号。
考虑到本仓库是公开仓库且曾有账号暴露，这一项应在 P4 前处理。

**体积问题：** 私有导出实测：

| 导出 | 持仓 | 源行 | 格式化字节 | 紧凑字节 |
| --- | --- | --- | --- | --- |
| 新图 | 18 | 26 | 480,617 | 280,075 |
| 旧图 | 15 | 23 | 418,449 | 244,101 |

格式化导出约每条持仓增加 20 KB。按此线性估算，约 45 条持仓即超过导入的 1 MiB 限制，导出的文件无法再导入，
不满足 P1「导出再导入保持语义一致」。这是估算，未用真实大图实测。

**修复要求：**

- 存入快照的原文遮蔽类似账号的片段（如 `U\d{5,}`、`DU\d+`），并在证据中注明已遮蔽。
- 原始识别结果与正文分开（例如单独导出，或 P4 的 `snapshot_recognition_runs`），或至少改为紧凑格式。
- 增加接近上限行数的往返测试，并让导出端在超过导入上限时明确提示。

### A5 — 账本入口写死 8798，识别服务未启动时页面打不开（中）

**位置：** `cost_basis.html` 新增导航；`tests/portfolio_snapshot.test.js:119–127` 断言了该地址。

**原因：** 链接指向 `http://127.0.0.1:8798/portfolio_snapshot.html`，而识别服务不随任何启动脚本启动。
服务未运行时入口直接连接失败，与计划 §4.2「识别服务不可用时，图片载入、校对和 JSON 导出仍可使用」不符。

**建议：** 改为相对链接，由前端 8000 端口提供页面。页面已会依次尝试本源与 `http://127.0.0.1:8798`，
服务也接受 loopback 的 HTTP 来源，因此识别应仍可工作。这是代码推断，尚未实测；修改时同步更新测试并做一次浏览器验证。

## 5. 对验收记录的意见

- **300/300 与 360/360 的口径：** 旧图基准 300 格中 72 格为空，新图 360 格中 81 格为空。
  其中币种、交易所、乘数共约 44（旧图）/ 53（新图）格是解析器从不填写的字段，属于必然匹配。
  实际由识别读出并比对的约为 228 / 279 项。记录已说明「包含明确未知」，建议同时列出两个数字。
- **重复性：** Apple Vision 对同一输入是确定性的，同图三次一致不能说明稳健性。
  计划 §6.4 要求的缩放、裁剪、JPEG 压缩版本尚未测试，A1 的拉宽模拟也属于这一类。
- **基准来源：** 两份逐字段基准由代理目读得出，验收记录已说明尚未经用户签核。进入 P3 前应由用户逐行确认。
- **验证器：** `scripts/verify_portfolio_snapshot_ocr.py` 只比对源行数量，不比对每个源行的类型（分组 / 组合 / 未分类）。
  计划 §6.4「层级与去重」要求分类与对应关系，建议在基准中加入逐行 `rowType`。

#### R1 — 表头中出现未知列名时仍接受，值落入相邻列（中，属 A1）

#### R2 — 持仓行下方的缩进装饰行使该持仓降为「未分类」（中，属 A3）

**位置：** `js/portfolio_snapshot_ocr.js:243–250`。

### 14.2 §22.5 的真实行为

1. Vision 已纳入数值复核的字段：首读合法、3×/4× 一致且与首读不同，包括正负号不同时，
   数值为 null；保留 `originalValue`、`conflictingReadings.first/reread`，问题文字显示双方读数，
   不作为已采纳的数字更正进入批量确认。行身份改变的 DAILY P&L 同样处理。
2. 首读合法且与一致复读相同，记录 `confirmed`。
3. **复读缺失或 3×/4× 自身不一致时，仍保留首读并标记 `unchecked`**，并非所有不一致都清空；
   问题提示会出现在疑点中，人工修改后相应未复核提示不再适用。
4. 首读缺失时，仍允许一致复读补值。AVG PRICE 继续既有 R10，RapidOCR 继续协议 2。
   因此本轮不能关闭「多次识别可能同错」这一一般性问题，也不能扩称所有数值均已三方校验。
