# Cost Basis 导入完整性：当前行为与修复验收

更新：2026-09-19。包含 R01–R20 / V01–V12 后续修复、全年重建/遮罩账户、C/O 反向开仓及随机状态机发现的批次问题。
范围：当前工作区的 Activity/Flex/TWS 导入、版本保护、报表覆盖和备份恢复。历史问题与反例保留在两份 review 文档；本文件描述修复后的实现。

基本原则：账本是事实来源；TWS 快照只发现差异，不自动记账。报表中的指派现金只包含标的交割，不能重复计入开仓权利金。TWS 成交是提前入账的证据，后续报表必须证明重复或提出冲突。

## 1. 用户操作流程

1. 先导入完整历史报表，逐行预览后确认。需要替换已有历史时选择“覆盖式整本重建”：它替换全部活动事件，不是替换某个月。提示会列出旧历史、新文件区间以及前后两端被缩短的部分。
2. 此后按月追加，不勾重建。没有成交的月份也可以导入；Period、账户和期末持仓等必要信息缺失时，不能宣称整月已完整核对。
3. 盘中可拉取并确认 TWS 真实成交；佣金/币种证据未齐时不能入账。后续 CSV 逐笔或按明确的订单聚合证据核对。
4. 提交前检查问题列表、新增/已存在/已核对数、净现金以及股票、期权、期货的持仓对照。存在问题时整批阻断，提交处理器也执行同样的门槛。
5. 账本标题下的“报表覆盖”只显示当前历史仍有效且完成必要检查的区间；导入过文件不等于该月份已经完整核对。区间外的首尾遗漏以及期末净仓为零的漏月，仍需与自己保留的连续月报核对。

修复与恢复方式：

- **相同券商引用被修订**：阻断并说明变更字段。使用修订后的完整累计报表整本重建；普通冲销不会释放引用，不能靠“冲销后重导同 ID”完成修订。
- **手工重复记录**：先核实，再冲销对应手工行，重新预览 CSV。指派、行权和到期等期权交割也参与重复检查。
- **期初存根**：补入更早的完整历史，程序核对新增历史的净数量，与存根恰好一致后在同一事务冲销存根。部分历史不能以另一笔开仓追加在存根旁边。
- **误冲销**：如果有误操作前的重建存档或 JSON 备份，可恢复它；普通冲销本身不会自动创建重建存档。没有合适存档时，需核实源记录并用完整历史重建。
- **JSON 备份**：当前导出由后端在一个读事务中取得完整事件及摘要，不依赖浏览器分页缓存。文件恢复前检查格式、摘要及账户/标的/币种/类型，显示事件数量和日期范围，明确确认后才替换。当前历史先存档；作废状态等事件审计字段保留。文件恢复后需重新导入报表建立覆盖证明。
- 新文件格式为 `cost-basis-backup` version 1。旧版没有摘要的临时 JSON 导出不作为可直接恢复文件；请保留原文件，通过当前版本重新导出，或使用 SQLite 一致性备份恢复。页面文件恢复上限为 7 MiB，给当前 8 MiB WebSocket 请求限制留出封装空间；大型完整数据库备份使用 README 的 SQLite 一致性流程。没有自动备份调度。

## 2. 身份、修订和重复核对

每行先生成唯一的来源引用 `sourceRef`，完全相同行先加 occurrence 后缀，再执行别名匹配。确认的重复行进入 `confirmedDuplicates`，不再改写成可能碰撞的新引用。

- 同引用先比较种类、日期、账户、合约、数量、价格、费用和现金；可用的券商身份及换月目的合约也参与比较。不再因“引用存在”而跳过修订检查。
- 直接命中 `ibkr-exec-<sourceRef>` 也必须核对经济项，不能仅凭 ID 宣告已核对。
- 跨格式精确匹配按账户、合约、秒数和经济项，一条已有记录每批只能被认领一次。多条相同成交数量不对称时，剩余歧义行阻断，不静默丢弃。
- 同秒同合约、引用不同的疑似数量/价格/费用修订会进入冲突。累计文件若以原引用及相同经济内容完整保留旧行，该旧行已被交代清楚，不再充当另一条新增成交的修订候选；同日现金行适用同样规则，跨格式别名不能代替原引用证据。日期缺时分秒而可能与已有记录重叠时阻断，不伪造秒数，也不当作确定新成交。
- 手工交易、期权指派/行权/到期，以及同日同额的手工股息/费用有重复守卫。无法证明是独立交易的记录需要先核实，系统不猜测归属。
- FUT 换月保留来源两腿；两腿已被核对才能整体去重，部分重叠阻断。
- 原格式无券商唯一 ID 时仍依赖内容指纹。内容或时间发生变化可能产生歧义；此时采用明确阻断和完整历史重建，不承诺自动识别所有券商修订。

Order / Trade 分笔：

- 子行经过与主交易行相同的缺佣金、数字、日期、币种等校验，且账户、合约和币种必须与父行一致。
- 数量、带符号佣金、净现金和打印精度内的加权价均须核平；相互矛盾时整批阻断。
- 只有通过上述检查才能匹配已有 fill 并导入剩余分笔。无子行时仍使用现有 permId 分组/连续成交段及金额、均价检查。

## 3. 期初、期末和输入检查

期初推导以报表期末、报表有效变动和截至 cutoff 已持有的账本仓位为依据。

- 没有成本证据的股票期初残差阻断。有已知 Basis、但没有任何成交的首份报表可以生成期初余额，日期采用明确 Period 起点前一天；无法确定日期时在预览阶段阻断。
- Activity 遮罩账户只有可见前后部分匹配且用户确认当前文件归属后才绑定完整账号；换文件/账本使确认失效。不同完整账户、可见部分不匹配及缺失账户仍阻断；报表区间取正文，不猜文件名。
- 期权期初在完整平仓 Basis、数量和损益恒等式成立时恢复为 `prior_basis`；缺证据才生成明确标示的零权利金 `prior_open`，矛盾证据阻断。股票同样只在成本可归属时生成期初草稿。
- Activity 与 Flex 都向存根规划传递正确账户；新增历史在存根日期前的净开平仓数量须恰好重建存根。已存来源行不被重复用于证明替换数量。
- 有持仓行却没有 Summary、坏数量、矛盾乘数、错币种、提到本标的但不可解析的合约，均不能被解释为“期末零持仓”。
- 缺少行币种时要求导出该字段；不会把缺失证据显示成币种相符。
- 交易主行与分笔子行的数字须整体可解析，未闭合引号拒绝；缺佣金不能默认零。无 proceeds 列的允许推导路径仍标记 cashDerived。
- 股息撤回为负现金，税款退款为正现金；返佣/退款使用明确标签，存储层允许相应现金方向。
- 无 Trades 的完整月报也会核对区间内未认领 TWS，包含持仓已归零的一开一平；不能仅因期末仓位为零而漏掉现金差异。
- includeInCost=false 在前后端均表示持仓和现金整体不参与。
- 同笔 C/O 保留为一条 `ibkr_close_open`，必须确实平掉已有反向持仓并开出余量；纯 C 超额与纯 O 抵消仍拒绝。现金、佣金和来源引用不因反向拆成两份。
- 拆股组（2026-09-24）：批量导入与整本重建拒绝拆股组行，拆股只能在页面手工整组记录；报表里本标的的公司行动行仍是导入问题。已入账的拆股组参与导入核对：C/O 分笔重标把转换行展开为转出、转入两部分并按拆股代次识别合约；TWS 批量对账的账本张数证明同样计入转换后的持仓；每次导入写入后，后端重新证明该账户的所有拆股组，补录的拆股前历史若改变了当时持仓，整批拒绝。

## 4. 版本、事务和覆盖生命周期

- 读取新文件立即清除旧预览；迟到读取与 TWS 响应按账本及 generation 丢弃。
- 一次账本分页读取的所有页面必须使用相同 digest，事件数据和该页 digest 来自同一个数据库读事务。混合版本、不完整分页或超过读取上限时，不能发布有效预览。
- 预览绑定账本身份、版本、文件与模式。提交期间禁止换文件/账本；迟到提交结果不能清除另一个预览。重建计划也绑定请求时的账本/generation，不能以新计划凭据升级旧预览。
- 导入/重建在同一事务内先写入整批，再按日期、券商时间及序号校验完整受影响历史；任何失败回滚事件、覆盖登记和存档。预览为新行分配与数据库一致的追加序号，同秒行不插到旧开仓前。重建不因引用已在待移除旧历史中而跳过文件行。
- 乘数推导先收集整批有效显式乘数及适用保留历史；多个可能乘数不能回退默认值，须显式提供。单条追加适用相同歧义保护。
- 导入、重建、清空、存档恢复和文件恢复在服务端要求完整 bookIdentity 和 expectedLedgerVersion；旧入口不再因为省略凭据而放行。固定 token 保留幂等重试行为。
- 当前 schema **v9**。v8 的批次登记仍保留为审计记录；升级时标记其覆盖证明失效，因为无法可靠推回它属于哪一代重建历史，事件本身不修改。
- 重建/清空/恢复时，当前批次登记与事件一起存档；恢复旧存档时恢复它的登记。更早且没有覆盖存档的版本按“没有覆盖证明”处理。
- 手工补录、冲销和导入改变某日历史时，该日及以后的旧核对证明失效，审计登记仍保留；本次实际完成检查的报表可重新登记。
- 展示覆盖至少需要明确 Period、账户、可读期末持仓；追加还需要修订与 TWS 覆盖检查。整本重建不与被替换的旧历史做重复核对。未核实/已失效月份不合并进“已覆盖”。
- 存档事件及覆盖记录在恢复时校验摘要；失败整批回滚。JSON 文件摘要用于检测损坏，不代表外部文件已经通过券商真实性认证。
